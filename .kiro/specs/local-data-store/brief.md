# Brief: local-data-store

> 制約の正本は `/AGENTS.md`。シードデータは `.kiro/steering/exercise-seed.md`。

## Problem

本アプリは「どのメディアがどの種目か」というユーザーが手で与えた情報が唯一の価値の源泉である。この情報が失われる、または壊れると、ユーザーがタグ付けに費やした労力が丸ごと無駄になる。にもかかわらず、それを保持する永続化層が存在しない。

さらに、このスペックは**開発機の Windows 上で完全にテストできる唯一のスペック**である。UI も写真ライブラリも介さず、Node 上の vitest だけで正しさを検証できる。Apple Developer Program の承認待ちの間に進められる数少ない作業でもある。

## Current State

- 永続化層が存在しない。データベースもスキーマも未定義
- マイグレーション戦略が未確立

## Desired Outcome

- SQLite スキーマが定義され、型安全なマイグレーションが適用できる
- 初回起動時に 8 部位 / 54 種目がシードされ、ユーザーはすぐにタグ付けを始められる
- ユーザーが種目を追加・編集・削除でき、**シード由来かどうかによる区別が存在しない**
- 上位層は SQL を直接書かず、リポジトリ層の API を通じてメディア・種目・タグを読み書きできる
- スキーマ変更時に既存ユーザーのデータが失われないマイグレーション経路が確立している
- **リポジトリ層とクエリ組み立てのロジックが、Node の vitest だけで完全にテストできる**

## Approach

`expo-sqlite` + Drizzle ORM を採用する。Drizzle は型安全なスキーマ定義とマイグレーション生成を提供し、New Architecture 対応済みの expo-sqlite の上で動作する。WatermelonDB はクラウド同期のためのエンジンであり、同期バックエンドを持たない本アプリには過剰。MMKV は関係クエリを持たないため種目別グルーピングに使えない。

想定するテーブル構成:

- `body_parts` — 部位カテゴリ（胸・背中・肩・腕・脚・尻・体幹・全身の 8 件）
- `exercises` — 種目。日本語名、**エイリアス（スペース区切りの単一テキスト列）**、所属部位（**1 対多**）、表示順、論理削除フラグ。**`is_preset` に相当する列を持たない**
- `media_assets` — 取り込んだメディアの参照メタデータ。写真ライブラリのアセット ID、メディア種別、作成日時、再生時間、ファイル名、参照状態（有効 / 参照切れ）。**サムネイルのキャッシュパス列は持たない**
- `media_exercise_tags` — メディアと種目の**多対多**関連
- `app_settings` — 表示設定、最終同期時刻など

1 本の参考動画が複数種目を含む（コンパウンドセット、複合種目の解説動画など）ことは現実に起きるため、メディアと種目の関係は多対多とする。一方、種目と部位は 1 対多とする（`/AGENTS.md` §6）。

`media_assets` が作成日時・再生時間・ファイル名を保持するのは、**参照切れが起きた後にユーザーが手で選び直すときの手掛かり**としてである。これらは後から遡って取得できないので最初から保持する。ただし**自動同定ロジックは書かない**。

リポジトリ層は、アセットの実体がどこにあるか（写真ライブラリ参照かアプリ内コピーか）に依存しない API を公開する。将来の方針転換で上位層を書き換えずに済ませるための境界である。

**クエリ組み立てとグルーピングのロジックは React に依存しない純粋関数として書く**（`/AGENTS.md` §0）。これが Windows 上でのテストを成立させる前提である。

## Scope

- **In**:
  - Drizzle スキーマ定義と型の生成
  - マイグレーションの生成・適用機構、およびアプリ起動時のマイグレーション実行
  - 8 部位 / 54 種目のシードデータ定義と初回投入（`.kiro/steering/exercise-seed.md`）
  - 設定からの「初期種目を再投入」（既存種目と名前が衝突するものはスキップ）
  - 種目の CRUD（作成、名称変更、部位変更、エイリアス編集、削除時の既存タグの扱い）
  - メディアメタデータの CRUD
  - メディア ↔ 種目タグの付与・削除・一括操作
  - グルーピング / 検索のためのクエリ API（種目別、日付別、部位別、未分類の抽出、参照切れの抽出）
  - **エイリアスを含む種目検索**（日本語名と英字エイリアスの両方にヒットする `LIKE` 検索）
  - リポジトリ層とクエリロジックの vitest による単体テスト
  - DB 破損時・マイグレーション失敗時のフォールバック方針
- **Out**:
  - 写真ライブラリからの実際のアセット読み込み（`media-library-sync` が所有）
  - サムネイルの生成・キャッシュ（`media-library-sync` が所有。**このスペックはサムネイルに一切関与しない**）
  - UI コンポーネント
  - 種目の並べ替え UI
  - クラウド同期、バックアップ、エクスポート

## Boundary Candidates

- スキーマとマイグレーション: 変更理由はデータモデルの進化
- 種目・部位のシードデータ: 変更理由は筋トレのドメイン知識の見直し
- リポジトリ層 API: 変更理由は上位層が必要とするクエリの追加
- クエリ最適化 / インデックス: 変更理由はメディア件数増大に伴う性能問題

## Out of Boundary

- 写真ライブラリという外部システムとの接続を一切持たない。純粋にローカル永続化のみ
- 種目の自動判定・推論ロジックを持たない（サジェストは `tagging-workflow` が所有）
- 表示順やグルーピングの見せ方の決定は `library-browser` が所有する。ここはクエリ API を提供するに留める
- トレーニングログに相当するテーブルを作らない

## Upstream / Downstream

- **Upstream**: なし（`app-foundation` と並行実行可能。ただしパッケージ追加で package.json が競合しうるため調整が必要）
- **Downstream**: `media-library-sync`（メタデータの書き込み先）、`tagging-workflow`（種目とタグの読み書き）、`library-browser`（グルーピングクエリの消費者）

## Existing Spec Touchpoints

- **Extends**: なし
- **Adjacent**: `app-foundation` と同時期に進行し、双方が package.json / TypeScript 設定を触る
- **Adjacent**: `media-library-sync` と「参照状態」「再照合の手掛かりとなるメタデータ」の表現を合意すること

## Constraints

- `expo-sqlite` + Drizzle ORM を使用する。New Architecture 環境で動作すること
- **ユーザーが手で付けたタグは復旧不可能な資産である。マイグレーションでの欠損を許容しない**
- 写真ライブラリのアセット ID は恒久キーではない。**外部キーとして信頼してはならない**
- メディア件数は数百〜数千件を想定。一覧表示のクエリがこの規模で実用的な速度を保つこと
- **リポジトリ層とクエリロジックは Node の vitest から直接呼べること**（React / Expo モジュールへの依存を持ち込まない）
