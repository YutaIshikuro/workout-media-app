# Brief: tagging-workflow

> 制約の正本は `/AGENTS.md`。シードデータは `.kiro/steering/exercise-seed.md`。

## Problem

手動タグ付けが本アプリにおける分類の唯一の手段である。つまり**タグ付けの摩擦がそのままアプリの生死を決める**。1 本ずつ画面遷移して種目を検索して選ぶような設計だと、数十本溜まった時点でユーザーは諦め、アプリは「取り込んだが分類されていないメディアの山」になって価値がゼロになる。

さらに、連続タグ付けの速さは本アプリの差別化 3 点のうちの 1 つである。写真アプリでも「共有 → アルバムに追加」で分類はできるが、1 本ずつしかできない。ここで勝てなければアプリを作る理由が 1 つ減る。

参考動画は SNS を見ている最中にまとめて画面録画されることが多く、同じ日・近い時刻に同じ種目の動画が複数保存される傾向がある。この性質を利用しないと、入力量が実際より大きくなる。

## Current State

- タグ付けの手段が存在しない
- 未分類メディアを見つける導線がない
- 種目の選択 UI が未設計

## Desired Outcome

- 未分類のメディアがどれだけ残っているかが一目で分かり、そこから連続でタグ付けを始められる
- 1 本のメディアに対して、種目を選ぶまでのタップ数が最小である
- 複数のメディアをまとめて選び、同じ種目を一括で付与できる
- 直近使った種目、および同日・近接時刻のメディアに付けた種目が候補として上位に出る
- 種目名の一部（日本語・英字エイリアス・略記のいずれでも）で目的の種目に届く
- 目的の種目がマスタにない場合、タグ付けの流れを中断せずその場で新規作成できる
- 1 本のメディアに複数種目を付けられる
- 付けたタグを後から編集・削除できる

## Approach

未分類メディアを「キュー」として提示し、連続処理を前提とした UI にする。1 本タグを付けたら自動で次のメディアに進む流れにして、画面遷移のコストを消す。

サジェストを 3 段構えで用意する:

1. **近接メディア継承** — 同日・近接時刻に取り込まれた直前のメディアに付けた種目を最上位に出す。まとめ保存された動画群を高速に処理できる
2. **直近使用種目** — 最近使った種目を頻度順で並べる
3. **部位カテゴリからの絞り込み** — 上記に該当しない場合、部位（8 カテゴリ）で絞ってから種目を選ぶ

検索は日本語名と英字エイリアスの両方にヒットさせる。エイリアスには略記（`bp` `dl` `rdl` `sq` `ohp`）が含まれるので、ジムで 2 文字打てば目的の種目に届く。

一括タグ付けは、複数選択モードで対象を選び、種目を 1 回選ぶだけで全件に付与する形とする。

種目のその場作成は、種目検索で該当がなかったときに「"◯◯" を新しい種目として追加」を検索結果の末尾に出す形で、フローを中断せずに済ませる。**シード由来の種目とユーザー作成の種目に区別はない**ので、作成後の扱いは完全に同じである。エイリアスは任意入力（空でよい）。

**サジェストのランキングロジックは React に依存しない純粋関数として書く**（`/AGENTS.md` §0）。近接メディア継承の時刻しきい値、直近使用の頻度重み、検索スコアリングは、すべて Node の vitest でテストする。

## Scope

- **In**:
  - 未分類メディアのキュー表示と件数バッジ
  - 連続タグ付けフロー（付与 → 自動で次へ）
  - 種目選択 UI（検索、部位カテゴリ絞り込み、候補サジェスト）
  - **近接メディア継承サジェスト**（純粋関数）
  - **直近使用種目サジェスト**（純粋関数）
  - **日本語名 + 英字エイリアスの検索**（純粋関数）
  - 複数選択による一括タグ付け
  - 1 メディアへの複数種目付与
  - 種目のその場作成（検索結果からの新規作成導線）
  - 付与済みタグの編集・削除
  - タグ付けのスキップ / 対象外マーク（筋トレと無関係なメディアを除外する）
  - 一括操作の取り消し（誤って大量付与した場合の救済）
  - タップ数の測定と要件としての明示
  - Maestro flow（キューからの連続タグ付け、一括タグ付け、その場作成）
- **Out**:
  - AI / ML による種目の自動判定
  - 種目マスタの管理画面（`local-data-store` のリポジトリ API を使って別途）
  - 種目の並べ替え UI
  - メディアの取り込み（`media-library-sync` が所有）
  - タグ付け済みメディアの閲覧・グルーピング表示（`library-browser` が所有）

## Boundary Candidates

- 未分類キューと連続処理フロー: 変更理由は入力効率の改善
- 種目選択 UI（検索・絞り込み）: 変更理由は種目数の増大
- サジェストロジック: 変更理由は推薦精度の改善
- 一括操作: 変更理由は大量処理のユースケース変化

## Out of Boundary

- 写真ライブラリへのアクセスを持たない。`media-library-sync` が取り込んだ結果のみを扱う
- 閲覧・検索・グルーピングの表示を担わない。タグを「付ける」側のみ
- 種目の自動推論を行わない。サジェストは直近履歴と時刻近接に基づく**決定的なルール**であり、推論モデルではない
- トレーニングログの入力を一切扱わない

## Upstream / Downstream

- **Upstream**: `local-data-store`（種目マスタとタグの読み書き、種目の作成）、`media-library-sync`（タグ付け対象となる取り込み済みメディアと参照状態）
- **Downstream**: `library-browser`（タグが付いていることが閲覧体験の前提）

## Existing Spec Touchpoints

- **Extends**: なし
- **Adjacent**: `library-browser` と種目タグの多対多モデルを共有する。両者が `local-data-store` の同一リポジトリ API を経由し、独自クエリを持たないこと

## Constraints

- **入力摩擦の低さが機能要件そのものである。タップ数を要件として明示的に測ること**
- 参照切れ状態のメディアがキューに混入しうる。その場合の扱いを定義すること
- **ユーザーが付けたタグは復旧不可能な資産である。一括操作の誤爆に対する取り消し手段が必須**
- 種目数はシード 54 件 + ユーザー作成で数十〜百数十件を想定。この規模で検索が即応すること
- **サジェストと検索のロジックは Node の vitest から直接呼べること**（React / Expo モジュールへの依存を持ち込まない）
- ジムでの片手・短時間操作が主要な利用場面
