## ② 限定アクセスがアプリ再起動後に再要求されるか

### 測定値

**再要求されない（no）。再現率 3/3。**

Expo Go を完全終了して再起動する試行を 3 回行い、いずれも画面マウント時点で以下が返った。

```
mount: status=granted privileges=limited canAskAgain=true
```

`undetermined` に戻った回はゼロ。加えて、**選択済みアセットも再起動をまたいで保持された**。

| 起動時刻 | 開始時に見える動画 | 終了時に見える動画 |
|---|---|---|
| 22:10 | 3 件 | 4 件 |
| 22:13 | **4 件**（前回の終了時と一致） | 11 件 |
| 22:17 | **11 件**（前回の終了時と一致） | 9 件 |

### 副次的な発見: ピッカーは「追加」ではなく「選択集合の編集」である

`presentPermissionsPicker()` の前後で見える件数は、3→4、4→6、6→11 と増えた一方、**11→9 と減った回もある**。

つまりこの API は置換でも追加でもなく、ユーザーが選択集合を自由に編集するものである。**一度取り込んだアセットが、ユーザーのピッカー操作で見えなくなりうる。**

### 要件への影響

- `/AGENTS.md` §6 の「取り込みの入口をシステムピッカーに統一し、限定アクセスを縮退状態ではなく主経路として設計する」方針は**成立する**。全件アクセス併用への方針変更は不要
- `media-library-sync` の**参照切れ検出は、2 つの異なる原因を同じ症状として受け取る**:
  1. メディアが実際に削除された（復旧不能）
  2. 限定アクセスの選択から外された（**選び直せば復旧する**）

  JS から両者を区別する手段は確認できていない。したがって UI の文言を「削除されました」と断定してはならない。「見つかりません。選び直してください」のように、両方の原因を包含する表現にする
- 参照切れが**ユーザー自身の操作で日常的に発生しうる**ことになるため、`/AGENTS.md` §6 の「参照切れは検出して一覧に印を出し、ユーザーが選び直す」導線は例外処理ではなく通常の導線として設計する

### 方針変更の要否

**不要。** ただし上記の参照切れ 2 原因の扱いは `media-library-sync` の要件に明記すること。

### 未確認

- **「1 回目のライブラリアクセス時に権限を確認された」という体感とログが食い違っている。** 実測は 1 回目 92 / 129 / 151 ms、2 回目以降 17〜19 ms。権限ダイアログが実際にブロックしていれば人間の操作を挟むため秒単位になるはずで、この差はメディアストアの初期化コストと考えるのが自然である。iOS の限定アクセスのリマインダーバナー（ブロックしない表示）を見た可能性が高いが、確認していない
- **Expo Go のコンテナで測っている。** 写真ライブラリの権限は Expo Go に紐づくため、ここで測ったのは Expo Go の権限の挙動である。FormCatalog 自身の挙動は development build で再確認すること。ただし「iOS の限定アクセスが再起動で飛ぶか」という OS 側の挙動については有力な第一報とみなす

## 測定項目外の発見（API の形）

計画になかったが、設計に直接効く事実が 2 つ判明した。型定義の実物（`node_modules/expo-media-library/build/types/`）で確認した。

### `exeForMetadata()` の返り値に `uri` が含まれない

`AssetMetadata` が持つのは `id` / `filename` / `mediaType` / `width` / `height` / `duration` / `creationTime` / `modificationTime` / `isFavorite` のみ。公式ドキュメントにも「URI のような重いフィールドが要るときは `Asset` の getter を使え」とある。

- **`local-data-store` への含意**: 参照切れの手掛かりとして `/AGENTS.md` §6 がスキーマに保持を求めている作成日時・再生時間・ファイル名は、**すべて安いクエリ 1 回で取得できる**。個別の getter を呼ぶ必要はない
- **`library-browser` / `media-library-sync` への含意**: サムネイル生成と再生には、**アセットごとに `getUri()` または `getInfo()` の非同期呼び出しが 1 回増える**。グリッドのスクロール性能に直接効くため、④の測定では URI 解決を独立したバケットとして計測する

### `Asset` は `id` だけを持つ軽量ハンドルである

`uri` / `filename` / `duration` / `width` / `height` はいずれもプロパティではなく **async getter**（`getUri()` / `getFilename()` / …）。個別に呼ぶと 1 アセットあたりの往復が積み上がる。まとめて必要なときは `getInfo()` を 1 回呼ぶ形にすること。

## 環境上の制約（`app-foundation` の README に反映すること）

**WSL2 の既定（NAT）では、iPhone 実機が Metro に到達できない。** Metro が出す URL は WSL の内部アドレス（`172.22.x.x`）であり、同一 LAN 上の iPhone からは到達できない。症状は Expo Go 側の「Opening project...」のままタイムアウト。

- 回避策 1: `npx expo start --go --tunnel`
- 回避策 2: `.wslconfig` の `networkingMode=mirrored`。ただし**これは WSL 2.0.0 以降の機能**であり、古い WSL（本環境では 1.2.5.0）では**設定を書いても黙って無視される**。`wsl --update` が必要
- 併発しやすい別要因: **CLI 側の Expo ログイン漏れ**。iOS の Expo Go 57 は CLI と端末の双方で同一アカウントのログインを要求する
- 無害なノイズ: WSL に GUI ライブラリがないため `react-native-devtools` が `libatk-1.0.so.0` 不足で起動に失敗する。Metro の動作には影響しない

これは `app-foundation` の要件 1.5（LAN で到達できない場合のトンネル手順を README に書く）に直接対応する実測情報である。

### 測定ログの取り方

測定②はアプリの完全終了と再起動が手順に含まれるため、**端末画面上のログは消える**。測定行は Metro のターミナル（PC 側）に `[spike:<画面名>]` 付きで出力し、`npx expo start --go 2>&1 | tee ~/spike-log.txt` でファイルに残すこと。

### 次にやること（人間の手作業）

1. **実機 UDID を EAS に登録する** — `npx eas-cli@latest device:create` を **`workout-media-app` の外**で実行し、Website 方式で発行された URL / QR を iPhone で開いてプロファイルを入れる。新規メンバーシップでは Apple 側の処理に 24〜72 時間かかるので、他の作業より先に投げておく
   - リポジトリ内で `eas init` / `eas build:configure` を実行しないこと。`eas.json` は `eas-delivery` の所有物であり、`app.json` は `app-foundation` のタスク 4.2 が所有する
2. **③の測定** — 写真ライブラリの権限を**全件アクセス**に切り替えてから「全件（動画）」「ページング」「全メディア件数」を実行する。限定アクセスの 3〜11 件では母数が小さすぎて所要時間の見積もりに使えない
3. **④の測定** — 「20 本を計測」を 1 回。グリッドに実際に描画されるかまで確認する
4. **①の測定** — 目視判断が要るため最後に、時間を取って行う。短尺（5〜10 秒）の画面録画を対象にすること
5. **②を development build で再確認** — UDID の処理が通ってから。Expo Go のコンテナではなく FormCatalog 自身の権限で測り直す

### 測定時の注意

- 測定は**アプリを閉じずに同一セッション内で続ける**。閉じると初期化コストが cold からやり直しになる
- ログは `npx expo start --go 2>&1 | tee ~/spike-log.txt` で必ずファイルに残す
- 接続がタイムアウトする場合は `--tunnel` を付ける（「環境上の制約」の節を参照）
